Supabase × OpenF1 · build plan

Parc Fermé

Before each Grand Prix, friends pick the podium and the pole sitter, and on a sprint weekend the Sprint too. Picks lock when qualifying starts, like cars in parc fermé. Once OpenF1 publishes the race results, the scores come in within a minute and the season's leaderboard updates live for everyone.

01 · Architecture

How the parts connect

There's one frontend, one Supabase project and two Edge Functions. Each function has its own schedule. The browser never calls OpenF1 directly. Only the functions do, and they write into Postgres, which the app reads from.

Postgres + RLSHolds all the rules. Picks are locked at the database, so a modified client can't get around them.
Calendar sync, twice a dayFetch the meetings in the next 4 weeks and upsert them. For a meeting that starts within 7 days, also fetch its sessions and drivers, even if the meeting is already stored. It runs twice because OpenF1's free tier is closed around live sessions, so one run can fail.
Per-minute check, run by the databaseThe cron job checks Postgres for a race that's waiting for results. It calls score-races only if it finds one, so most minutes cost nothing.
Scoring in TypeScriptscore-races calculates each player's points once, when results arrive, and stores them in scores. The leaderboard is a plain view over that table, with one table per season.
02 · Race weekend

From calendar to scores

Grand Prix picks lock at the start of Grand Prix qualifying, because pole is one of the picks. A sprint weekend has a second set of picks for the Sprint. Those lock at the start of sprint qualifying on Friday, and the Sprint is scored on its own on Saturday. The timeline shows the Grand Prix.

04 · Signing in

Magic links and Google

There are no passwords. People sign in either with Google or with a link sent by email, called a magic link. Signing in and creating an account are separate screens, so the sign-in screen only ever sends a link to an email that already has an account. Typing a stranger's address into it does nothing.

The three calls

// Supabase must allow this URL: Authentication → URL Configuration → Redirect URLs
const redirectTo = `${location.origin}/auth/callback`;

// Sign in: existing accounts only, so nobody can use this form to send email to strangers
await supabase.auth.signInWithOtp({
  email,
  options: { shouldCreateUser: false, emailRedirectTo: redirectTo, captchaToken },
});

// Create account: the display name is stored on the user and copied into profiles by the trigger
await supabase.auth.signInWithOtp({
  email,
  options: { shouldCreateUser: true, data: { display_name }, emailRedirectTo: redirectTo, captchaToken },
});

// Google, on either screen. A first-time Google user gets an account automatically.
await supabase.auth.signInWithOAuth({ provider: "google", options: { redirectTo } });

Every new user gets a profile

create function public.handle_new_user()
returns trigger language plpgsql security definer set search_path = '' as $$
begin
  insert into public.profiles (id, display_name)
  values (
    new.id,
    coalesce(new.raw_user_meta_data ->> 'display_name',   -- from Create account
             new.raw_user_meta_data ->> 'full_name',      -- from Google
             'Player')                                    -- never the email: every player sees names
  );
  return new;
end $$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();

Keeping the email form from being abused

  • The sign-in form reveals whether an email has an account. It shows "no account for this email", so anyone can check whether a given address has signed up. That's acceptable for a friends' league, and invite-only sign-up makes it moot.
  • The link signs in the device that opens it. If someone asks for a link on their laptop and opens it on their phone, the phone is signed in, not the laptop. The check-email screen should say "open it on this device". To support cross-device sign-in, add the 6-digit code ({{ .Token }}) to the email template and a code field that calls verifyOtp.
05 · Data model

Seven tables, three views

  }
  sessions {

  profiles {

  }
  results {
    int session_key PK "race or sprint session"
    int p1
    int p2
    int p3
    int pole
  }
  scores {
    uuid user_id PK
    int session_key PK "race or sprint session"
    int points
  }

The calendar tables store what OpenF1 returns: one row per meeting, one per session, and one per driver per session. scores is written by score-races, one row per player per race or sprint.

drivers is keyed by (session_key, driver_number) because car numbers can change between seasons. Lando Norris raced as #4 and is #1 in 2026. Predictions and results point at drivers through (session_key, p1) and the like, so a pick can only name a driver on that race's entry list.

The rest is built with views:

  • races: one row per Grand Prix and one per Sprint, told apart by kind. Each is joined to its own qualifying session to get lock_at. Cancelled sessions are left out. The app and the RLS policies use this view.
  • races_unscored: races that ended in the last 2 days and have no results yet. The per-minute cron job uses it to decide whether to call score-races.
  • leaderboard: one table per season. It has each player's total, races played, best race, points from the last weekend, rank and previous rank, summed from scores. Only races with a results row count.

All three views use security_invoker, so they follow the same RLS rules as the tables. The schema is in supabase/migrations/: …_schema.sql holds the tables and views in plain Postgres, and …_supabase.sql adds Auth, the RLS policies and Realtime.

06 · OpenF1 mapping

Where each value comes from

Our columnEndpointHow
meetings.*/meetings?date_start>=…&date_start<=…Twice a day, for today through today + 28 days. Each meeting_key is one weekend, stored as soon as it appears.
sessions.*/sessions?meeting_key=…Only for a meeting that starts within 7 days of the run, including one already stored. That run fetches the most up-to-date session times.
drivers.*/drivers?meeting_key=…Same meetings as the sessions row. It returns the entry list for every session of the weekend, and it works before the weekend starts. Some rows come back twice, so drop duplicates before the upsert.
results.p1–p3/session_result?session_key=…&position<=3Race or Sprint classification.
results.pole/session_result?session_key=<quali>&position=1Uses the qualifying result (sprint qualifying for a Sprint), not /starting_grid, because grid penalties can move the pole sitter back.
07 · Scoring

13 points for a Grand Prix, 8 for a Sprint

PickRuleGrand PrixSprint
Podium driverEach picked driver who finishes on the podium, in any position1 × 31 × 3
Exact P1Bonus for the winner in the right position+4+2
Exact P2 / P3Bonus for each in the right position+2 each+1 each
PoleFastest in that race's qualifying: GP qualifying, or sprint qualifying for a Sprint21
Perfect score138

The rules live in supabase/functions/score-races/scoring.ts, a plain TypeScript function with no Deno or Supabase imports. npm run test:functions checks it against the example race from the mockups. Changing the points is a code change there, not a database migration.

A Sprint keeps the podium point and halves the bonuses. A fastest-lap pick was dropped from the first version. The README's "Later" list says how to bring it back.

08 · The important SQL

Races, locks, scores and schedules

A race is a Race or Sprint session plus its own qualifying session

create view races as
select r.session_key,
       r.meeting_key,
       case r.session_name when 'Race' then 'race' else 'sprint' end as kind,
       m.year,
       m.meeting_name,
       m.circuit_short_name,
       q.session_key as quali_session_key,
       q.date_start  as lock_at,
       r.date_start  as race_start,
       r.date_end    as race_end
from sessions r
join meetings m on m.meeting_key = r.meeting_key
join sessions q on q.meeting_key = r.meeting_key
  and q.session_name = case r.session_name when 'Race' then 'Qualifying' else 'Sprint Qualifying' end
where r.session_name in ('Race', 'Sprint')
  and not r.is_cancelled;

create view races_unscored as
select ra.*
from races ra
left join results res on res.session_key = ra.session_key
where res.session_key is null
  and ra.race_end < now()
  and ra.race_end > now() - interval '2 days';  -- give up after 2 days

Drivers belong to a session, and picks must be on the entry list

create table drivers (
  session_key   int  references sessions,
  driver_number int,
  name_acronym  text not null,
  full_name     text not null,
  team_name     text,
  team_colour   text,
  primary key (session_key, driver_number)   -- numbers can change between seasons
);

create table predictions (
  user_id     uuid references auth.users on delete cascade,
  session_key int  references sessions,          -- the race or sprint session
  p1 int, p2 int, p3 int, pole int,
  primary key (user_id, session_key),
  -- each pick must be a driver on this race's entry list
  foreign key (session_key, p1)   references drivers,
  foreign key (session_key, p2)   references drivers,
  foreign key (session_key, p3)   references drivers,
  foreign key (session_key, pole) references drivers,
  check (p1 <> p2 and p1 <> p3 and p2 <> p3)
);
-- results: the same four foreign keys

Picks can only be changed before the lock

-- a prediction can be written only by its owner, and only before lock_at
alter table predictions enable row level security;

create policy "write own before lock" on predictions
  for insert to authenticated
  with check (
    user_id = auth.uid()
    and exists (select 1 from races r
                where r.session_key = predictions.session_key
                  and now() < r.lock_at)
  );
-- same condition for update (in both using and with check)

-- you always see your own picks; everyone else's show up after the lock
create policy "read own, or all after lock" on predictions
  for select to authenticated
  using (
    user_id = auth.uid()
    or exists (select 1 from races r
               where r.session_key = predictions.session_key
                 and r.lock_at <= now())
  );

-- meetings, sessions, drivers, results: select for authenticated; no write policy,
-- so only the Edge Functions (service role) can write to them

Scores are stored; the leaderboard is a view, one table per season

create table scores (
  user_id     uuid references profiles on delete cascade,
  session_key int  references sessions on delete cascade,   -- the race or sprint session
  points      int  not null check (points >= 0),
  primary key (user_id, session_key)
);

create view leaderboard with (security_invoker = on) as
with scored as (                                       -- only races that are done
  select s.user_id, s.points, ra.year, ra.meeting_key, ra.race_start
  from scores s
  join results r on r.session_key = s.session_key
  join races ra  on ra.session_key = s.session_key
),
latest as (                                            -- each season's last scored weekend
  select distinct on (year) year, meeting_key
  from scored
  order by year, race_start desc
),
totals as (
  select sc.year, sc.user_id,
         sum(sc.points)::int as total, count(*)::int as races, max(sc.points) as best_race,
         coalesce(sum(sc.points) filter (where sc.meeting_key = l.meeting_key), 0)::int as last_points,
         count(*) filter (where sc.meeting_key <> l.meeting_key) as races_before
  from scored sc
  join latest l on l.year = sc.year
  group by sc.year, sc.user_id                         -- by id: two players can share a name
)
select t.year, t.user_id, pr.display_name, t.total, t.races, t.best_race, t.last_points,
       rank() over (partition by t.year order by t.total desc, t.best_race desc)::int as rank,
       case when t.races_before > 0                   -- no earlier score: no previous rank
            then rank() over (partition by t.year order by t.total - t.last_points desc)::int
       end as prev_rank
from totals t
join profiles pr on pr.id = t.user_id
order by t.year desc, rank, pr.display_name;

Two cron jobs

-- The functions check the new secret API key, sent in an apikey header.

-- 1. calendar: twice a day, at 06:00 and 18:00 UTC
select cron.schedule('sync-calendar', '0 6,18 * * *', $$
  select net.http_post(
    url     := (select decrypted_secret from vault.decrypted_secrets where name = 'project_url')
               || '/functions/v1/sync-calendar',
    headers := jsonb_build_object('apikey',
               (select decrypted_secret from vault.decrypted_secrets where name = 'secret_key'))
  );
$$);

-- 2. scoring: every minute, but calls the function only when a race is waiting for results
--    the schedule string is the polling setting: re-run cron.schedule('score-races', '*/5 * * * *', ...)
--    with the same name to change it
select cron.schedule('score-races', '* * * * *', $$
  select net.http_post(
    url     := (select decrypted_secret from vault.decrypted_secrets where name = 'project_url')
               || '/functions/v1/score-races',
    headers := jsonb_build_object('apikey',
               (select decrypted_secret from vault.decrypted_secrets where name = 'secret_key'))
  )
  where exists (select 1 from races_unscored);
$$);

The Edge Functions

Both are in supabase/functions/ and accept only the secret API key, because only pg_cron calls them. Each has a core.ts with the job and a short index.ts that makes it an Edge Function. The jobs reach OpenF1 only through _shared/openf1.ts and the database only through _shared/db.ts, so a Node server with a scheduler can run the same core.ts files.

  • sync-calendar/core.ts: upserts the meetings for the next 4 weeks. For a meeting starting within 7 days it also upserts its sessions and entry list, dropping OpenF1's duplicate rows first. In dev, POST {"from": "2025-10-01", "to": "2025-10-10"} to sync a past window instead.
  • score-races/core.ts: for each race or sprint in races_unscored, fetches the podium and pole. If the podium isn't published yet it tries again next run. Otherwise it scores every player with scoring.ts, upserts scores, then inserts the results row.

Steps, in order

Vue 3 + Vite + TypeScript + Vue Router in the parc-ferme repo, with the source in app/ using Nuxt's folder names (pages/, layouts/, composables/). A later move to Nuxt only replaces router.ts and main.ts.

    npm i vue vue-router @supabase/supabase-js
npm i -D vite @vitejs/plugin-vue typescript@^6 vue-tsc

    TypeScript stays on 6.x for now, because vue-tsc doesn't run on TypeScript 7 yet.

  2. Start the local Supabase stack

    supabase init

supabase start               # Docker must be running; the first run downloads images

    Studio is at http://127.0.0.1:54323. Magic-link emails land in the test inbox at http://127.0.0.1:54324. Linking the hosted project (supabase link --project-ref …) waits until you go live.

  3. Put keys in .env.local, never in code

    # TODO: Securely load this value from an environment variable or secrets vault. Do not hardcode.
VITE_SUPABASE_URL=<API URL from supabase status or the dashboard>

    Only the publishable key goes to the browser. The secret key stays on the server side, in Vault for the cron jobs.

  4. Turn on Auth

    Under Authentication in the hosted dashboard, set up the pieces from section 04:

    • URL Configuration: add the production /auth/callback URL. Locally, supabase/config.toml already allows http://localhost:5173/auth/callback.
    • SMTP: connect your own email provider. Supabase's built-in sender is for testing only and has a very low limit.
    • Attack Protection: turn on Turnstile. Rate Limits: keep the defaults to start.

  5. Apply the migration

    supabase db reset   # local: rebuilds the database from supabase/migrations/
supabase db push    # hosted, once linked

    The first migration holds the seven tables and three views. The second holds the RLS policies, the handle_new_user trigger and Realtime for results. pg_cron and pg_net come in a second migration with the cron jobs.

  6. Run the tests

    supabase test db        # database rules: lock, sprints, seasons, entry list, visibility

  7. Run the Edge Functions locally, then deploy

    supabase start serves both functions at http://127.0.0.1:54321/functions/v1/<name>. Call them with an apikey header holding the local secret key from supabase status. Check that meetings, sessions and drivers fill up and that the races view returns rows.

    supabase functions deploy sync-calendar
supabase functions deploy score-races

  8. Store secrets in Vault and schedule both cron jobs

    Store project_url and secret_key with select vault.create_secret('<value>', '<name>') in the SQL editor, pasting the values there rather than into any file. Then run both cron.schedule statements from section 08.

    In dev, project_url is not 127.0.0.1: the database runs inside Docker and reaches the functions through Docker's internal network.

  9. Test scoring against a past race

    POST a 2025 date window to sync-calendar, enter a few picks by hand, then call score-races. The 2-day cutoff in races_unscored excludes an old race, so for this test, adjust the race's date_end or call the scoring directly. You get the whole flow working without waiting for a race weekend.

  10. Build the eight screens

    Sign in, create account, check your email, picks (with a countdown to lock_at), the driver picker, picks locked, the leaderboard (subscribed to results inserts) and profile. The mockups are in design/mockups.html (mobile) and design/desktop.html.

10 · Before you build

Things to check

  • OpenF1 lists future weekends. Confirmed. /meetings returns upcoming meetings, and /drivers?meeting_key=… returns the entry list before the weekend starts.
  • How soon free data appears. OpenF1 only charges for live data. Historical data is free, but the docs don't say how soon after a race it's published. Per-minute checks until then cost nothing, and after 2 days the race is dropped from races_unscored.
  • Picks open when the entry list is published. The pick form needs the race's sessions (for lock_at) and its entry list. Sessions are fetched once the weekend is within 7 days. OpenF1 publishes entry lists at different times: Singapore 2026 had one 2 weeks ahead, the 2 Oct 2026 weekend had none 5 days ahead. That's why the sync runs twice a day (about 6 requests a day).
  • OpenF1 answers 404 when nothing matches. Not an empty list. Both functions treat a 404 as "no rows yet".
  • Late entry-list changes. If a reserve driver is announced on Thursday, they won't be in the picker until sync-calendar runs again. The same manual re-run covers this.
  • Disqualifications after the race. A result row is written once. If the stewards change the result within 2 days, delete the results row: the leaderboard stops counting that race, and the next minute rescores it and overwrites scores. After 2 days, call score-races by hand.
  • Email delivery limits. Check your SMTP provider's free tier and sender-domain setup (SPF and DKIM) early. Magic links that land in spam look like a broken sign-in.
  • OpenF1 is closed around live sessions. The free tier answers nothing from about 30 minutes before a session to 30 minutes after it. Results can't arrive sooner than that, and a calendar sync that lands in that window fails, which is why it runs twice a day.
  • Leagues. This plan has one leaderboard per season for everyone. Private leagues for different friend groups would need a leagues table plus a membership table, and an extra condition in each policy. Add them only if you need them.
