Supabase × OpenF1 · build plan

Parc Fermé

Before each Grand Prix, friends pick the podium, pole sitter and fastest lap. Picks lock when qualifying starts, like cars in parc fermé. Once OpenF1 publishes the race results, the scores come in within a minute and the leaderboard updates live for everyone.

01 · Architecture

How the parts connect

There's one frontend, one Supabase project and two Edge Functions. Each function has its own schedule. The browser never calls OpenF1 directly. Only the functions do, and they write into Postgres, which the app reads from.

Postgres + RLSHolds all the rules. Picks are locked at the database, so a modified client can't get around them.
Weekly calendar syncEvery Monday, fetch the meetings in the next 4 weeks and upsert them. For a meeting that starts within 7 days, also fetch its sessions and drivers, even if the meeting is already stored.
Per-minute check, run by the databaseThe cron job checks Postgres for a race that's waiting for results. It calls score-races only if it finds one, so most minutes cost nothing.
Scoring is a viewPoints are calculated when the leaderboard is read, so there's no scores table to keep in sync.
02 · Race weekend

From calendar to scores

Picks lock at the start of Grand Prix qualifying, because pole is one of the picks. On sprint weekends, sprint qualifying happens on Friday and doesn't count.

04 · Signing in

Magic links and Google

There are no passwords. People sign in either with Google or with a link sent by email, called a magic link. Signing in and creating an account are separate screens, so the sign-in screen only ever sends a link to an email that already has an account. Typing a stranger's address into it does nothing.

The three calls

// Supabase must allow this URL: Authentication → URL Configuration → Redirect URLs
const redirectTo = `${location.origin}/auth/callback`;

// Sign in: existing accounts only, so nobody can use this form to send email to strangers
await supabase.auth.signInWithOtp({
  email,
  options: { shouldCreateUser: false, emailRedirectTo: redirectTo, captchaToken },
});

// Create account: the display name is stored on the user and copied into profiles by the trigger
await supabase.auth.signInWithOtp({
  email,
  options: { shouldCreateUser: true, data: { display_name }, emailRedirectTo: redirectTo, captchaToken },
});

// Google, on either screen. A first-time Google user gets an account automatically.
await supabase.auth.signInWithOAuth({ provider: "google", options: { redirectTo } });

Every new user gets a profile

create function public.handle_new_user()
returns trigger language plpgsql security definer set search_path = '' as $$
begin
  insert into public.profiles (id, display_name)
  values (
    new.id,
    coalesce(new.raw_user_meta_data ->> 'display_name',   -- from Create account
             new.raw_user_meta_data ->> 'full_name',      -- from Google
             split_part(new.email, '@', 1))               -- fallback
  );
  return new;
end $$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();

Keeping the email form from being abused

ProtectionWhat it stopsWhere to set it
shouldCreateUser: falseThe sign-in form sending email to addresses that have no account.The sign-in call above.
Per-address cooldownRepeated taps sending a pile of emails to one person. The "Resend link in 0:42" countdown in the app shows this limit.Authentication → Rate Limits (60 seconds by default).
Project-wide email limitA script sending thousands of links through your project.Authentication → Rate Limits.

  • The sign-in form reveals whether an email has an account. It shows "no account for this email", so anyone can check whether a given address has signed up. That's acceptable for a friends' league, and invite-only sign-up makes it moot.
  • The link signs in the device that opens it. If someone asks for a link on their laptop and opens it on their phone, the phone is signed in, not the laptop. The check-email screen should say "open it on this device". To support cross-device sign-in, add the 6-digit code ({{ .Token }}) to the email template and a code field that calls verifyOtp.

Six tables, four views

  sessions {
    int session_key PK
    int meeting_key FK
    text session_name "Race, Qualifying, Sprint..."
    timestamptz date_start
    timestamptz date_end
  }
  profiles {
    uuid id PK "= auth.users.id"
    text display_name
  }
  drivers {
    int session_key PK "FK sessions"
    int driver_number PK
    text name_acronym
    text full_name
    text team_name
    text team_colour "hex, for UI"
  }
  predictions {
    uuid user_id PK
    int session_key PK "race session"
    int p1
    int p2
    int p3
    int pole
    int fastest_lap
  }
  results {
    int session_key PK "race session"
    int p1
    int p2
    int p3
    int pole
    int fastest_lap
  }

The tables store what OpenF1 returns: one row per meeting, one per session, and one per driver per session.

drivers is keyed by (session_key, driver_number) because car numbers can change between seasons. Lando Norris raced as #4 and is #1 in 2026. Predictions and results point at drivers through (session_key, p1) and the like, so a pick can only name a driver on that race's entry list.

The rest is built with views:

  • races: one row per Grand Prix, joining the race session to its qualifying session to get lock_at. The app and the RLS policies use this view.
  • races_unscored: races that ended in the last 2 days and have no results yet. The per-minute cron job uses it to decide whether to call score-races.
  • prediction_points and leaderboard: scoring, using security_invoker so they follow the same RLS rules as the tables.
06 · OpenF1 mapping

Where each value comes from

Our columnEndpointHow
meetings.*/meetings?date_start>=…&date_start<=…Weekly, for today through today + 28 days. Each meeting_key is one weekend, stored as soon as it appears.
sessions.*/sessions?meeting_key=…Only for a meeting that starts within 7 days of the run, including one already stored. That run fetches the most up-to-date session times.
drivers.*/drivers?meeting_key=…Same meetings as the sessions row. It returns the entry list for every session of the weekend, and it works before the weekend starts. Some rows come back twice, so drop duplicates before the upsert.
results.p1–p3/session_result?session_key=…&position<=3Race classification.
results.pole/session_result?session_key=<quali>&position=1Uses the qualifying result, not /starting_grid, because grid penalties can move the pole sitter back.
results.fastest_lap/laps?session_key=…The lowest non-null lap_duration. That's about 1,200 rows per race, which is fine for one request.

08 · The important SQL

Races, locks, scoring and schedules

A race is a Race session plus its Qualifying session

create view races as
select r.session_key,
       r.meeting_key,
       m.meeting_name,
       m.circuit_short_name,
       q.session_key as quali_session_key,
       q.date_start  as lock_at,
       r.date_start  as race_start,
       r.date_end    as race_end
from sessions r
join meetings m on m.meeting_key = r.meeting_key
join sessions q on q.meeting_key = r.meeting_key and q.session_name = 'Qualifying'
where r.session_name = 'Race';

create view races_unscored as
select ra.*
from races ra
left join results res on res.session_key = ra.session_key
where res.session_key is null
  and ra.race_end < now()
  and ra.race_end > now() - interval '2 days';  -- give up after 2 days

Drivers belong to a session, and picks must be on the entry list

create table drivers (
  session_key   int  references sessions,
  driver_number int,
  name_acronym  text not null,
  full_name     text not null,
  team_name     text,
  team_colour   text,
  primary key (session_key, driver_number)   -- numbers can change between seasons
);

create table predictions (
  user_id     uuid references auth.users on delete cascade,
  session_key int  references sessions,          -- the race session
  p1 int, p2 int, p3 int, pole int, fastest_lap int,
  primary key (user_id, session_key),
  -- each pick must be a driver on this race's entry list
  foreign key (session_key, p1)          references drivers,
  foreign key (session_key, p2)          references drivers,
  foreign key (session_key, p3)          references drivers,
  foreign key (session_key, pole)        references drivers,
  foreign key (session_key, fastest_lap) references drivers,
  check (p1 <> p2 and p1 <> p3 and p2 <> p3)
);
-- results: the same five foreign keys

Picks can only be changed before the lock

-- a prediction can be written only by its owner, and only before lock_at
alter table predictions enable row level security;

create policy "write own before lock" on predictions
  for insert to authenticated
  with check (
    user_id = auth.uid()
    and exists (select 1 from races r
                where r.session_key = predictions.session_key
                  and now() < r.lock_at)
  );
-- same condition for update (in both using and with check)

-- you always see your own picks; everyone else's show up after the lock
create policy "read own, or all after lock" on predictions
  for select to authenticated
  using (
    user_id = auth.uid()
    or exists (select 1 from races r
               where r.session_key = predictions.session_key
                 and r.lock_at <= now())
  );

-- meetings, sessions, drivers, results: select for authenticated; no write policy,
-- so only the Edge Functions (service role) can write to them

Scoring is a view

create view prediction_points with (security_invoker = on) as
select p.user_id, p.session_key,
    (select count(*) from unnest(array[p.p1, p.p2, p.p3]) d
      where d = any (array[r.p1, r.p2, r.p3]))::int     -- 1 per podium driver
  + (p.p1 = r.p1)::int * 4
  + (p.p2 = r.p2)::int * 2
  + (p.p3 = r.p3)::int * 2
  + (p.pole = r.pole)::int * 2
  + (p.fastest_lap = r.fastest_lap)::int * 2  as points
from predictions p
join results r using (session_key);

create view leaderboard with (security_invoker = on) as
select pr.display_name, sum(pp.points) as total, count(*) as races
from prediction_points pp
join profiles pr on pr.id = pp.user_id
group by pr.display_name
order by total desc;

The Edge Functions, in outline

// supabase/functions/sync-calendar/index.ts
import { createClient } from "npm:@supabase/supabase-js@2";
const API = "https://api.openf1.org/v1";
const get = (path: string) => fetch(API + path).then((r) => r.json());
const day = (d: Date) => d.toISOString().slice(0, 10);

Deno.serve(async () => {
  // TODO: Securely load this value from an environment variable or secrets vault. Do not hardcode.
  // (Supabase injects both into Edge Functions automatically.)
  const db = createClient(Deno.env.get("SUPABASE_URL")!, Deno.env.get("SUPABASE_SERVICE_ROLE_KEY")!);

  const from = new Date();
  const to = new Date(Date.now() + 28 * 24 * 3600 * 1000);
  const meetings = await get(`/meetings?date_start>=${day(from)}&date_start<=${day(to)}`);

  // upsert, not insert-if-missing, so moved or corrected times are picked up
  await db.from("meetings").upsert(meetings.map(pickMeetingColumns));

  // sessions and drivers only for a meeting that starts this week, even if it's already stored
  const weekAhead = Date.now() + 7 * 24 * 3600 * 1000;
  for (const m of meetings.filter((m) => Date.parse(m.date_start) < weekAhead)) {
    const sessions = await get(`/sessions?meeting_key=${m.meeting_key}`);
    await db.from("sessions").upsert(sessions.map(pickSessionColumns));

    // OpenF1 returns some rows twice, and one upsert can't touch the same key twice
    const drivers = await get(`/drivers?meeting_key=${m.meeting_key}`);
    const unique = [...new Map(drivers.map((d) => [`${d.session_key}:${d.driver_number}`, d])).values()];
    await db.from("drivers").upsert(unique.map(pickDriverColumns));
  }
  return new Response("ok");
});

// supabase/functions/score-races/index.ts (same setup as above)
Deno.serve(async () => {
  const { data: pending } = await db.from("races_unscored").select("*");
  for (const race of pending ?? []) {
    const podium = await get(`/session_result?session_key=${race.session_key}&position<=3`);
    if (podium.length < 3) continue;                      // not published yet
    const [pole] = await get(`/session_result?session_key=${race.quali_session_key}&position=1`);
    const laps = (await get(`/laps?session_key=${race.session_key}`)).filter((l) => l.lap_duration);
    const fastest = laps.reduce((a, b) => (b.lap_duration < a.lap_duration ? b : a));
    await db.from("results").insert({ session_key: race.session_key, /* p1..p3, pole, fastest_lap */ });
  }
  return new Response("ok");
});
09 · Setup

Steps, in order

This uses the same stack as handsup: Vite, TypeScript, supabase-js and CLI migrations. It goes in the parc-ferme repo.

  1. Scaffold the frontend

    npm create vite@latest . -- --template vanilla-ts   # inside parc-ferme/
npm i @supabase/supabase-js

  2. Create the Supabase project and link it

    Create a project in the dashboard, then run the commands below. supabase start runs a local stack in Docker, which is safer to experiment on.

    supabase init
supabase link --project-ref <your-project-ref>
supabase start            # optional: local stack

  3. Put keys in .env.local, never in code

    # TODO: Securely load this value from an environment variable or secrets vault. Do not hardcode.
VITE_SUPABASE_URL=<project URL from dashboard>
VITE_SUPABASE_ANON_KEY=<anon key from dashboard>

    Only the anon key goes to the browser. The service role key stays on the server side, in Edge Functions and Vault.

  4. Turn on Auth

    Under Authentication, set up the pieces from section 04:

    • Providers: enable Email and Google. Google needs an OAuth client from Google Cloud Console, with Supabase's callback URL as the authorised redirect URI.
    • URL Configuration: add http://localhost:5173/auth/callback for development and the production URL later.
    • SMTP: connect your own email provider. Supabase's built-in sender is for testing only and has a very low limit.
    • Attack Protection: turn on Turnstile. Rate Limits: keep the defaults to start.

    The handle_new_user trigger goes into the first migration.

  5. Write the first migration

    supabase migration new init
# tables: meetings, sessions, drivers, profiles, predictions, results
# views:  races, races_unscored, prediction_points, leaderboard
# RLS policies
supabase db push

  6. Enable extensions and publish results for Realtime

    create extension if not exists pg_cron;
create extension if not exists pg_net;
alter publication supabase_realtime add table results;

  7. Create and deploy both Edge Functions

    supabase functions new sync-calendar
supabase functions new score-races
supabase functions deploy sync-calendar
supabase functions deploy score-races

    Run sync-calendar once by hand (supabase functions serve, then curl it on localhost). Check that meetings, sessions and drivers fill up and that the races view returns rows.

  8. Store secrets in Vault and schedule both cron jobs

    Store project_url and service_key with select vault.create_secret('<value>', '<name>') in the SQL editor, pasting the values in there rather than into any file. Then run both cron.schedule statements from section 08.

  9. Test scoring against a past race

    Let sync-calendar accept optional from and to dates for testing, and point it at a 2025 weekend. Enter a few picks by hand. The 2-day cutoff will exclude an old race, so call score-races directly. You get the whole flow working without waiting for a race weekend.

  10. Build the three screens

    Sign in, the next race's pick form (dropdowns in team colours, with a countdown to lock_at), and the leaderboard, subscribed to results inserts.

10 · Before you build

Things to check

  • Whether OpenF1 lists future sessions. The weekly sync assumes /meetings?date_start>=<today> returns upcoming weekends. Check this first. If only past sessions are listed, the calendar has to come from somewhere else.
  • How soon free data appears. OpenF1 only charges for live data. Historical data is free, but the docs don't say how soon after a race it's published. Per-minute checks until then cost nothing, and after 2 days the race is dropped from races_unscored.
  • Picks open on Monday of race week. The pick form needs the race's sessions (for lock_at) and its entry list, and both are fetched that Monday. Before then, the weekend shows as coming soon.
  • A failed Monday run. If it fails, that weekend has no sessions and no pick form. The job is safe to re-run, so run it by hand. Or schedule it daily: each run is about 3 requests.
  • Late entry-list changes. If a reserve driver is announced on Thursday, they won't be in the picker until sync-calendar runs again. The same manual re-run covers this.
  • Disqualifications after the race. A result row is written once. If the stewards change the result within 2 days, delete the row and the next minute scores the race again. After that, call score-races by hand.
  • Email delivery limits. Check your SMTP provider's free tier and sender-domain setup (SPF and DKIM) early. Magic links that land in spam look like a broken sign-in.
  • Leagues. This plan has one global leaderboard. Private leagues for different friend groups would need a leagues table plus a membership table, and an extra condition in each policy. Add them only if you need them.
